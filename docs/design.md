# Локальная дизайн-студия с облачным AI

Дата: 2026-10-03. Статус: утверждена пользователем 2026-10-03.

## Цель и согласованные условия

Создать отдельный инструмент для проектирования интерфейсов: визуальный редактор
реальных React-компонентов, интерактивный просмотр и управление агентом из внешнего
чата через локальный MCP. Данные принадлежат пользователю, сохраняются в обычные
файлы и публикуются в GitHub. AI может работать через облако.

Файлы проекта позволяют продолжить работу без истории предыдущего чата. GitHub
содержит последнюю опубликованную версию, локальная папка — также неопубликованные
изменения. Доступ агента зависит от доступности репозитория и разрешений его среды;
живой контекст редактора доступен только при запущенной и подключённой студии.

Код студии размещается в отдельном репозитории. Дизайн продукта хранится в его
репозитории, например `design/` в product-repository. Независимые проекты получают свои
репозитории. Этот документ находится в product-repository как результат обсуждения;
реализацию студии следует начинать в отдельном рабочем каталоге.

## Границы первой версии

Один пользователь, один открытый проект и одна активная сессия редактора.
Поддерживаются несколько экранов, варианты экрана, локальные ассеты, библиотека
компонентов, редактирование свойств и порядка компонентов, undo/redo, комментарии,
просмотр на разных ширинах и Git-синхронизация.

Первая версия не включает свободное векторное рисование, импорт Figma, совместное
редактирование, встроенный облачный чат, генерацию изображений, произвольный импорт
React-приложения и автоматическую синхронизацию макета с исходным кодом продукта.
Прототип не обращается к рабочей базе продукта: используются локальные фикстуры.

## Пользовательский сценарий

1. Пользователь запускает студию и выбирает разрешённую папку проекта.
2. Студия проверяет структуру проекта и состояние Git, показывает локальную и
   опубликованную версии. Проверка удалённой ветки не изменяет рабочие файлы.
3. Пользователь открывает экран, добавляет компоненты и редактирует их свойства.
4. Он выделяет элемент и обращается к подключённому агенту во внешнем чате.
5. Агент получает структуру экрана, выделение, библиотеку и правила, создаёт
   предложение изменений. Пользователь видит затронутые элементы и сравнение.
6. Предложение применяется одной отменяемой операцией. При явно запрошенной правке
   агент может сразу применить её через тот же механизм; повторное подтверждение
   на каждую правку не обязательно.
7. Пользователь проверяет результат в интерактивном просмотре и при необходимости
   отменяет операцию. Принятое решение можно записать в локальный документ.
8. Команда «Сохранить версию» создаёт коммит выбранных изменений. «Опубликовать»
   выполняет push текущей ветки. Если сеть недоступна, коммит остаётся локально.
9. На другой машине пользователь получает опубликованный коммит и открывает проект.

## Интерфейс

- Слева: экраны, варианты, компоненты и ассеты.
- В центре: выбранный экран, рамка выделения и переключатель ширины просмотра.
- Справа: свойства элемента, комментарии и предложения агента.
- В верхней панели: проект, активный экран, undo/redo и сохранение версии.
- В строке состояния: состояние записи на диск, MCP и Git, включая ошибки.

В интерфейсе явно различаются «Сохранено локально», «Есть изменения без коммита»,
«Есть неопубликованные коммиты», «Опубликовано», «Удалённая ветка изменилась» и
«Ветки разошлись». Нельзя показывать «Опубликовано» после одного локального commit.

## Архитектура и единицы ответственности

Предлагаемый стек: TypeScript, React, Vite, Puck для визуального редактирования,
Node.js для локального сервиса, схема с runtime-валидацией, MCP SDK и системный Git.
Версии и фактическую совместимость библиотек проверяет технический пилот до
фиксации зависимостей. Первая поставка — браузер и локальный сервис, без desktop-оболочки.

| Единица | Ответственность | Зависимости |
| --- | --- | --- |
| Модель документов | Формат, валидация, миграции, стабильные идентификаторы | Библиотека схем |
| Реестр компонентов | Разрешённые компоненты, свойства, токены и демонстрационные данные | React, адаптер продукта |
| Движок изменений | Применение операций, ревизии, undo/redo, проверка конфликтов | Модель документов |
| Файловое хранилище | Чтение, атомарная запись, восстановление и наблюдение за файлами | Движок, файловая система |
| Редактор и просмотр | Визуальные действия, выделение, интерактивное отображение | Puck, реестр, локальный API |
| MCP-адаптер | Доступ агента к документам, предложениям и активной сессии | Тот же локальный API |
| Git-адаптер | Status, fetch, commit, push и безопасное обновление | Системный Git, файловое хранилище |

Puck — адаптер визуального редактора. Каноническая модель студии принадлежит студии;
внутренний формат стороннего редактора не должен становиться единственной копией данных.
Совместимость Puck с такой моделью и вложенными компонентами — предмет первого пилота.

## Файлы проекта

```text
design/
  studio.project.json
  brief.md
  design-system/
    registry.json
    tokens.json
    rules.md
  screens/
    budget-default.json
    budget-empty.json
  fixtures/
    budget.json
  assets/
  comments/
    budget-default.json
  proposals/
  decisions/
  previews/
  README.md
```

`studio.project.json` содержит `schemaVersion`, стабильный `projectId`, название,
версию требуемого адаптера компонентов и перечень экранов. Абсолютные локальные
пути и учётные данные в него не записываются. Реестр описывает компоненты и схемы
свойств; исполняемый React-код поставляет установленный адаптер, а не JSON-файл.

Экран содержит `schemaVersion`, `screenId`, `revision`, название, корневые узлы,
параметры просмотра и ссылку на фикстуру. Узел содержит стабильный `id`, `type`,
`props` и именованные вложенные `slots`. Ссылки на токены хранятся явно. Вариант —
отдельный экран с полем `variantOf`; удаление исходного экрана не удаляет вариант.

Произвольный JavaScript, HTML-скрипты и внешние URL ассетов не принимаются как
свойства документа. Разрешённые интеракции задаются схемой адаптера и работают
с локальными данными. Неизвестный компонент вызывает диагностическую заглушку,
его данные сохраняются; редактирование такого узла запрещено до установки адаптера.

Комментарии имеют собственные идентификаторы, привязку к экрану и необязательному
узлу, текст и статус. После удаления узла комментарий остаётся как непривязанный.
Принятые решения сохраняются в Markdown и объясняют выбор варианта и ограничения.
Содержимое чата автоматически целиком в репозиторий не копируется.

## Общий механизм ручных и агентских изменений

Любое изменение проходит через движок операций. В первой версии разрешены:
`insertNode`, `updateProps`, `moveNode`, `removeNode`, `setViewport`.
Создание и копирование экрана выполняются отдельными проверяемыми командами.

Пакет операций содержит `requestId`, `screenId`, `baseRevision`, описание и
массив операций. Движок проверяет существование узлов, уникальность ID, отсутствие
циклов, допустимость слотов, схемы свойств и ссылки на ассеты. Обновление свойств
использует разрешённые поля схемы; свободные пути к объектам не принимаются.

Если `baseRevision` отличается от текущей ревизии, пакет отклоняется целиком с
ошибкой `REVISION_CONFLICT`. Агент перечитывает документ и готовит новую правку.
Автоматического слияния изменений экрана в первой версии нет.

Успешный пакет повышает ревизию и создаёт одну запись undo. Undo/redo также
повышает ревизию: устаревший ответ агента не может примениться после отмены.
Повторный `requestId` с тем же содержимым возвращает прежний результат, а с другим
содержимым отклоняется. Квитанции операций сохраняются в локальном служебном журнале
и проверяются относительно актуальной ревизии документа после перезапуска.

После изменения студия сообщает «Сохраняется», затем «Сохранено локально» только
после завершённой записи. Ошибка записи оставляет изменённое состояние и заметную
ошибку; закрытие не должно молча терять изменения. Запись использует временный
файл, синхронизацию и атомарное переименование. Второй писатель блокируется.
Внешнее изменение файла загружается при отсутствии несохранённых правок;
иначе показывается конфликт и сохраняется локальная восстановительная копия.

## Контракт взаимодействия с агентом

MCP в первой версии работает через stdio и использует установленный путь к
разрешённому проекту. Подключение к текущему чату зависит от настроек клиентского
приложения и проверяется отдельным smoke-тестом; наличие кода сервера не означает
успешное подключение. Произвольный доступ к файловой системе через MCP не выдаётся.

Предлагаемые инструменты:

- `project_read`: manifest, brief, правила дизайна и сведения об адаптере.
- `screens_list`: идентификаторы, названия и варианты.
- `screen_read`: документ и текущая ревизия.
- `components_list`: компоненты, допустимые свойства и слоты.
- `editor_context`: активный экран, выделение, ширина, доступность UI-сессии.
- `proposal_create`: сохранить и показать проверенный пакет без применения.
- `proposal_apply`: применить пакет при совпадении ревизии.
- `screen_variant_create`: создать копию со свежими ID и связью `variantOf`.
- `comments_read`: прочитать комментарии к экрану.
- `decision_write`: сохранить объяснение принятого решения в разрешённой папке.
- `git_status`: прочитать состояние локальной и удалённой версии.

MCP не предоставляет shell, установку пакетов и выполнение исходного кода из
промпта. Commit/push первоначально выполняются явными действиями пользователя
в студии либо обычными Git-инструментами агента в рамках его авторизации.

Если редактор закрыт, `editor_context` возвращает `EDITOR_DISCONNECTED`, а чтение
и изменение документов остаются доступны через локальный сервис. Получение
скриншота не входит в гарантии MCP первой версии: агент использует доступные ему
браузерные инструменты или сохранённое превью.

## GitHub и восстановление

Студия использует существующие Git credentials пользователя. Токены GitHub не
записываются в проект. При открытии выполняется fetch при доступной сети. Обновление
файлов возможно только отдельной командой, при чистом рабочем дереве и fast-forward.

При dirty tree, конфликтах или разошедшихся ветках студия прекращает обновление и
показывает причину. Не выполняются автоматические stash, rebase и force-push.
Локальное редактирование продолжает работать без сети. Ошибка push сохраняет
коммит и статус «Есть неопубликованные коммиты».

Коммит содержит только явно выбранные файлы проекта. Если проект находится в
репозитории продукта, изменения кода показываются отдельно и не добавляются
автоматически. Кэш, временные файлы, журналы и восстановительные копии находятся
в локальной `.studio/`, исключённой из Git. Превью генерируются заново; сохраняемые
контрольные изображения можно добавить явно. Крупные ассеты подключаются через
Git LFS при необходимости, без обязательной зависимости первой версии от LFS.

Восстановление версии начинается с отдельного checkout/worktree выбранного коммита,
а не с перезаписи текущей рабочей папки. Пользователь видит SHA и версию адаптера.
Чистый clone с установленным совместимым адаптером должен открываться без доступа
к прежней машине, браузерному localStorage или чату.

## Работа с облачным AI и локальным сервисом

Студия не содержит облачных API-ключей в первой версии: запросы отправляет внешний
AI-клиент. В облако попадают данные, которые агент передаёт модели в ходе задачи.
Локальное хранение и приватный GitHub не означают, что обработка AI остаётся локальной.

Локальный HTTP-сервис слушает loopback, проверяет origin и токен сессии. Он открывает
только заранее разрешённый корень проекта, отклоняет выход через `..` и symlink.
MCP использует этот же сервис для координации с редактором. Студия не подключается
к рабочим API продукта по умолчанию и не публикует прототип наружу.

## Технический пилот и порядок разработки

1. Проверить Puck: собственный компонент, вложенные слоты, выбор узла, изменение
   свойства и преобразование в канонический документ с сохранением ID.
2. Реализовать модель, движок ревизий и файловое сохранение. Получить работающий
   локальный просмотр и восстановление после перезапуска.
3. Подключить визуальные действия, варианты, комментарии и undo/redo.
4. Подключить MCP и проверить правку из реального внешнего AI-клиента.
5. Добавить Git-состояния, публикацию, получение изменений и восстановление версии.
6. Подключить адаптер product-repository и пройти приёмочный сценарий.

Пилот выполняется с небольшой демонстрационной библиотекой: Stack, Text, Button,
Card, Metric. Адаптер product-repository подключается после проверки архитектуры;
его компоненты не копируются навсегда в исходники студии. Первая интеграция требует
явных wrappers и mock providers для компонентов, зависящих от API или контекста.

Если Puck не сохраняет нужные ID/слоты через документированный API, пилот фиксирует
причину, и выбор редактора пересматривается до основной разработки. Прямой импорт
произвольного TSX и бесшовный экспорт в production-код не заявляются как готовые функции.

## Проверки и критерии приёмки

- Файл экрана проходит runtime-валидацию; неизвестная версия схемы не перезаписывается.
- После перезапуска восстанавливаются экран, варианты, комментарии и решения.
- Ручная и агентская правки изменяют одну модель, применяются атомарно и отменяются.
- Устаревший пакет агента не перезаписывает новую ручную правку.
- Повтор операции не создаёт дубликаты; invalid пакет не изменяет файл.
- Выход из разрешённой папки и запрос с неверным origin/token отклоняются.
- Отключение сети не препятствует редактированию и локальному commit.
- Неудачный push не отображается как успешная публикация.
- Новый clone воспроизводит сохранённый экран с совместимым адаптером.
- Экран бюджета имеет обычный, пустой и превышающий лимит варианты с локальными
  данными; их можно открыть на ширинах 390 и 1280 px и проверить интеракции.
- Реальный агент через MCP читает выделенный узел и меняет его свойство; проверка
  выполняется после фактического подключения, не только в unit-тесте.

Движок и хранилище проверяются unit/integration-тестами конфликтов, отказов записи,
повторов и перезапуска. Git-адаптер — временным локальным bare remote с diverged,
dirty и failed-push сценариями. Редактор — браузерным сценарием изменения и отмены;
визуальные результаты проверяются на обеих ширинах. Реальный GitHub нужен лишь
для завершающего smoke-теста публикации в выбранный пользователем репозиторий.

## Следующая стадия

После проверки этой спецификации подготовить отдельный подробный план технического
пилота и первого вертикального среза. Место и имя репозитория студии выбираются
при подготовке рабочей среды; они не влияют на формат файлов продукта. Подключение
MCP и создание удалённого репозитория выполняются как конкретные действия настройки,
а не считаются уже существующими возможностями.
